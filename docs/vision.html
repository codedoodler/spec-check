The vision

The living design contract

A system that reads every place your design is written down, keeps the requirements current, checks the spec against itself, and holds the code to it — continuously, from the first decision to the last commit.

1The problem: the one thing nothing checks

Type checkers catch syntax drift. Linters catch style drift. Tests catch the behaviour you thought to encode. Nothing reads the design and asks whether it still holds.

The system passes review on Monday. By Wednesday a change has violated a decision nobody remembers making — and the diff looks ordinary. When code can be rewritten in seconds, checking design intent stops being a nuisance and becomes the maintenance problem.

2The bet

Design intent can be made checkable — and once it is, it can be maintained automatically, from every source, forever.

1

Every decision carries a Check

The concrete thing you would look at to decide conformance. A requirement you cannot answer yes/no to is not a requirement yet — it is a wish.

2

Layers of trust

Deterministic checks where the rule is mechanical, an LLM only where judgment is genuinely required, and a verifier that won't let the model lie confidently.

3

"Unverifiable" is an answer

A tool built for trust must never guess. If it can't confirm something, it says so and hands it back.

3The whole loop

Each stage is useful alone. Together they turn a pile of scattered decisions into a contract the codebase is continuously held to.

1

Ingest — continuously, from everywhere

Meeting recordings, issue trackers, email, chat, discussion boards, specs, PRDs, ADRs, and files in the repo. Each statement becomes a [REQ] (a must) or an [INTENT] (a motivation), source-linked.

2

Model — the living requirements list

Deduplicated into four tiers, each with importance, status, and a What / Why / Check. Precedence is explicit: recent-wins, and supersede — never silently delete.

3

Resolve — the spec checks itself

Contradiction, supersession, duplication, ambiguity, orphan, staleness. Plus a derived priority ranking, so effort goes where it matters.

4

Conform — is the code still the design?

Deterministic checks settle the mechanical rules; an LLM judge reads the semantics; an evidence verifier catches overconfident verdicts. Each requirement ends pass · warn · fail · unverifiable.

5

Enforce — act on every change

On a pull request, push, or CI run: block a failing critical requirement, or warn — and always update the running violation tally.

6

Present — for humans and machines

A charted HTML view for people; structured JSON and an agent-readable entry point for machines.

7

Remember — the history of evolution

Every requirement's lifecycle, with source and date at each transition, and a time-travel view: what did the design say on a given date?

4The requirements model

A requirement is a small, checkable object — not a paragraph in a wiki.

Four tiers, four bars

TierHoldsTestable
A aspirationalthe guiding light — a goal, not a ruleno
B principlesinvariants; violating one is a defectconceptually
C componentwhat each part of the system must doyes
D testableeach becomes a testmechanically
The tiers matter because they are held to different bars — an aspirational goal can be partly met and still on track; a violated principle is a defect by definition.

The Check field is the whole point. Walk the list and any Check you cannot answer yes/no to is a red flag that the requirement is still too vague to enforce.

5The spec checks itself

A growing list will contradict itself. So the design is checked against itself, and every conflict has a defined handling.

ConflictMeaningHandling
Contradictiontwo active requirements cannot both holdprecedence; escalate if tied
Supersessiona newer decision overrides an older onemark the older superseded, keep it
Duplicatethe same requirement stated twicemerge, union the sources
Ambiguitya Check with two defensible readingsrewrite the Check to be binary
Orphanno owner, no check, nothing implements itflag; assign or retire
Stalenesscode no longer honours it and nobody re-affirmedre-affirm or retire
Precedence rule: the most recent ruling from a named authority wins; the loser is marked superseded and kept, never silently deleted. Anything the rule cannot settle is escalated as an open question — not guessed.

Priority, derived — not hand-waved

priority ≈ importance × tier_weight × dependency_count × violation_risk

Critical outranks high outranks medium; principles outrank component detail; how much else breaks if it is violated; and how likely it is to drift, from the running tally. The design tells you what to fix first.

6Enforcement: a gate, not a report

When code is submitted — whatever the resolution — the checks run against the change, and the system decides what to do about it.

BLOCK

A failing critical requirement stops the change — as a required status check. Drift never reaches the branch.

WARN + TALLY

A lesser violation is recorded, and the running tally is updated: which requirement, how often, trending how.

The tally is the real asset: it turns "the design is drifting" into a number you can watch, per requirement, over time. The sharpest signal is passing on Monday, failing on Wednesday — a requirement that was conformant and no longer is, which regresses against the design and should alert like one.

7The history of evolution

The design is not a snapshot. Every transition is recorded, so the list is a record you can trust and audit — not a mystery.

This yields two things almost nobody has today: an audit trail — who decided what, when, and based on which meeting or document — and time-travel: what did the design say on this date, and what changed since?

8The principles

Any contribution should protect these.

Measured, not typed. Prefer observing the real system over trusting a declaration.
Never guess. If it can't be confirmed, say unverifiable and hand it back.
Deterministic first. The cheapest, most certain method that works; an LLM only for genuine judgment.
Supersede, don't delete. History is the point; a silent removal destroys the audit.
Honest about limits. A tool for trust must not overstate what it knows.
